# Integrate X-Center ID

Register the relying-party app from the X-Center ID developer portal at https://id.xcenter.it/developer. The maintained contract is in [Identity](IDENTITY.md), and the native package is documented under [packages/expo](../packages/expo/README.md).

For a confidential backend authorization flow, register the backend's exact HTTPS callback as a web app. Keep the one-time client secret on that backend. For a public native authorization flow, choose Native app and register the product's OS-verified HTTPS app callback. Native registrations receive a client ID with no client secret. Each app must have its own registration and callback ownership. Publish the portal's TXT challenge at `_xcenter-id.<callback-host>` and activate the pending registration. Pending, restricted, revoked and unknown dynamic clients are unavailable for sign-in.

The reusable package exposes AccountEntry, RegisteredAppSignIn and authorizeNative. It supplies the account entry UI and a system-browser authorization flow with PKCE, state and nonce. The host app remains responsible for code exchange, ID token verification, its own account session, secure storage and recovery. Native access tokens are opaque. Pairwise issuer subjects differ between apps. Account-manager session endpoints are reserved for the account manager.

A backend must retain the login transaction before opening authorization, validate the token audience and stored nonce, and map users by issuer and subject. A client-supplied nonce at completion does not prove that the backend initiated the flow. Public native clients additionally depend on the actual app's verified Universal Links or Android App Links. A copied client ID or matching display name does not establish that ownership.

The installed **Integrate X-Center ID** skill and its repository source under `skills/integrate-xcenter-id` describe portal setup and the host integration decisions. An independent review verified that the instructions reject copied client identities and unsafe backend completion. Browser QA verified that app B cannot redeem app A's authorization code, a code cannot be reused, and an admin restriction makes a registered app unavailable. Actual OS callback ownership still requires testing the installed app.


The public developer documentation route is `/docs`. Package distribution currently uses `npm pack ./packages/expo` from an authorized checkout and installation of that archive into the target app; no public npm publication is claimed. `authorizeNative` and RegisteredAppSignIn accept supported `scopes`, a transaction `nonce` and `promptConsent` for incremental access. Existing defaults remain openid-only. Backend-based apps must create and retain their transaction and nonce before authorizing. The hosted API contract and its backend-key boundary are in [HOSTED_DATA.md](HOSTED_DATA.md).
